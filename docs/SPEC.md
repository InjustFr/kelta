# Kelta — Product spec

Kelta lets a developer take a ticket from their tracker (Jira, Redmine, GitHub Issues, GitLab Issues, Gitea Issues, Linear) and build it in a git worktree with **Claude Code and a terminal editor (nvim) side by side** in built-in terminals; review the PRs/MRs they are asked to review; move tickets; run tools (lazydocker, lazygit, sl web) inside the app; work on **several projects in one window**; extend everything with tools, triggers and plugin screens; configure everything through settings. Open source (MIT). macOS 13+ and Ubuntu 24.04+ (Hyprland, Sway, GNOME). It must be **fast and small** (ARCHITECTURE §13).

Glossary: **Project** = named set of local repos + tracker binding + code-host bindings + defaults. **Session** = one PTY process (Claude, nvim, shell, tool). **Tab** = split layout of panes within a project. **WorkItem** = ticket/review/branch ↔ worktree ↔ branch ↔ sessions ↔ PR link. **Queue** (the `inbox` pane) = one list across all open projects, ranked by whose move it is (FLOW §3). **Desk** = a work item's tab. **Library** = the Tickets and Pull requests lists (DESIGN §1.1).

A place renders outside any project and does not change the active project; anything it opens leaves it for the item's first project, else the active one. Kelta reopens on the last place, a global one or a project. Tools are not in the sidebar: a terminal tool opens zoomed in the current tab (§3.5).
- **Switching projects** never stops or pauses sessions; attention keeps updating in the sidebar. Target ≤ 50 ms warm.
- **Top bar** (`ContextBar`, 30 px, across the top of the window; DESIGN §6.3): `‹ ›` (`nav.back` / `nav.forward`), the breadcrumb of the selected sidebar row (a drag region), the search field (opens the palette), the project scope of the Queue, Tickets and Pull requests, the "needs you" chip (Claudes blocked on you, `⌘J`) and `+ New` (new work item, new session). On a work tab the **desk header** above its panes names the item instead: key, project, title, why, the stage track, the primary action and **Actions ⌘.** (FLOW §2.4). With custom decorations it is the window's title bar (macOS: traffic lights over its inset; Linux: Kelta's window buttons); with native ones the window title follows its breadcrumb.
- **Panes** contain: terminal, web tool, plugin screen, Tickets (list/board), Ticket detail, Pull requests, Review detail, Queue (`inbox`), WorkItem, Settings, Diagnostics, Welcome. Drag the gutter to resize; zoom a pane; move a pane to its own window (`pane.detach`, #342) and back; close a pane (a live session asks first: kill the process, move it to the background, or cancel; **background sessions** stay listed in the palette and the project's session list).
- **Command palette** (fuzzy): actions, projects, sessions across all projects (with status), tickets (cached), PRs, tools, plugin commands, settings sections.
- **Project switcher**: fuzzy list of configured projects (open or not); Enter opens/activates.
- **StatusBar**: app-wide state only: prefix, restart needed, Claude slots, rate limits, optional perf HUD (Kelta memory, separately from child processes). Hooks health ("Live status off") is in the pane header only.

## 2. Projects (multi-project)

- Create from folder: `project_detect` infers repos (git roots), remotes → code-host hints (github.com / gitlab host), tracker hints (Jira key pattern in recent branch names, `.github` presence). The "New project" sheet lets the user edit id, name, initial, colour, repos (primary + others, remote, base, code-host account) and a tracker account, which becomes a first ticket source in the global config (§3.4a). Worktree root and branch template, env, setup commands and the default session template are set afterwards in Settings (Project layer) or in the file. Writes `~/.config/kelta/projects/<id>.toml`.
- Several projects are open at once; open set and order persist. `kelta-ctl open <path>` opens/creates and focuses.
- Per-project groupings: tabs, layouts, sessions, work items, triggers, settings overrides, tickets/reviews views. Tools are not per project: they are personal and live in the global settings (§3.5).
- Aggregated views: **Tickets** and **Pull requests** (the Library, §1) span every open project's sources and every code-host account (unmatched PRs under **Other**). The **Queue** merges what needs you across projects into sections in the order to work in, grouped in three zones (Your move, Claude working, Waiting on others): Claude needs you, Ready for review, Next up, New for you, Fix, Review requests, Ship and clean up, In flight, Elsewhere (Claude sessions Kelta did not start, seen through the hook relay, `claude.hooks_offer`), Blocked (blocked tickets and their work, unless it needs you), Up next (my tickets). The sidebar's Queue row counts the Your move zone (`9 your move`).
- **Quitting Kelta** leaves the sessions running in the `keltad` session daemon (`terminal.session_host = "daemon"`); the next start re-attaches every live one where it was (shells, Claude, nvim keep their process and scrollback). Sessions that ended meanwhile restore as below. Quitting asks first: keep them running, or stop all sessions (and keltad); "Don't ask again" stores the answer in `app.quit_sessions`.
- Close project: sessions keep running unless "Close and stop sessions" is chosen. Remove project: moves config to `projects/.trash/`.

## 3. Core flows

### 3.1 Start work on a ticket
Entry points: Tickets/Board/Inbox (select + `Enter`→detail, **Start work** button or `Mod+Enter`; in the Tickets list `s` opens the plan sheet and `S` starts without it), palette "Start work on…", `kelta-ctl start SHOP-142 [--project shop]` (without `--project`: the default below; a guess shows the sheet), trigger action `start_work`, batch start (one Project field: "Usual project for each ticket" skips a ticket whose project is only a guess, or one project for all).

The project belongs to the work item (where the session runs), not to the ticket. Entry points pass only an explicit pick (the sheet's Project switch, `--project`, a trigger's `project_id`, a sub-task's parent work item's project) or none, never the active project nor the account's project; `work_plan { project_id?, source }` picks the default, first match wins:
- **Ticket:** (1) the project of an unfinished work item for this ticket, in any project: always a Resume there, with no picker (a closed project opens); with `another` (Start another PR, #456) a new item in that project instead, the ticket keeping its other items (FLOW §2.1); (2) the explicit pick; (3) the first route of the ticket's source matching its component, label or type: its project and, if it names one, its repo (a route to a closed project or one without a repository is skipped; a repo not in the project gives the primary); (4) the project of my most recent work item on a ticket of the same source (`WorkItem.ticket_source`; an older item without one counts when its account has a single source); (5) the source's first open project, marked `project_guessed` when it feeds several; (6) the active project, marked `project_guessed`. The ticket's source is the one using its account; when several do, the one whose cached views list the ticket, else the first in config order; none skips (3)-(5). The route's repo applies only in the route's project.
- **PR (Review locally):** (1) its work item's project; (2) the caller's project if it binds the PR's repo; (3) the first open project that does. None → refused with "No project has acme/web as a repository" and an **Open project settings** action.
- **Choices** (`project_choices`): open, non-Home projects with a repository, the ticket source's first; for a PR, those binding its repo. None → refused with "Add a repository to a project first" and an **Add project** action.

1. `work_plan` returns a **StartWorkPlan**, shown in a sheet (skipped when `work.plan_preview = false`, except when a choice is required, a guessed project included, even with `S`):
   ```
   StartWorkPlan { project_id, project_choices (picker if >1, first field; switching re-plans branch, worktree,
     Claude and side effects for that project), project_guessed (hint "No usual project for <source label, else account> tickets yet",
     focus on Project), source: Ticket{ticket}, repo_id (picker if >1; remembered per ticket; the source route's repo),
     base: "main", branch: "feat/SHOP-142-rate-limit-login" (template; validated with git check-ref-format),
     branch_exists: Option<{has_worktree, choice: Reuse|Suffix}> , worktree_path, template_id: "claude+editor",
     claude: {profile: "default", model, effort, permission_mode, prompt (rendered, editable)},
     side_effects: {assign_me: bool, transition_to: Option<target>, comment: Option<text>, run_setup: bool},
     existing: Option<WorkItemId>  // → sheet becomes "Resume"; None with `another` (a new item beside the ticket's, #456)
   }
   ```
   **Finish before starting** (#354, `work.finish_first`, default on): a new ticket start (never a Resume) with other work unfinished first lists it in the sheet, even with `S`: my unfinished work items, then my tickets in progress or in review with none (blocked ones included), each with its phase or status, closest to done first (merged, approved, in review, in progress). A row goes to that item; **Start anyway** (`Enter`) shows the plan; **Don't ask again** sets `work.finish_first = false`.
2. **Start** → `work_start` runs the journaled saga (each step idempotent; progress checklist in the sheet/toast; `Retry`/`Skip` per failed step):
   1. `ticket.before_start` (blocking triggers may veto with a message).
   2. Fetch ticket; write `<runtime>/s/<sid8>/ticket.md` (key, title, URL, status, labels, Markdown body, last 10 comments).
   3. `git fetch <remote> <base>` (20 s timeout; offline = warning), `git worktree add -b <branch> <path> <remote>/<base>` (or reuse); copy `worktree.include` globs (and `.worktreeinclude` patterns); add `.kelta/` to `.git/info/exclude`.
   4. Generate Claude files: `claude-settings.json` (hooks, ARCH §7.6), `mcp.json`, `context.md`.
      `context.md` (`--append-system-prompt-file`) holds what Kelta knows of the item, only the parts it has, with no network call: project, worktree, branch and base; the ticket (key, title, URL, path of `ticket.md`, a ticket linked after the fact included); the PR under review (URL, target); the item's own PR, from the review feed's cache: number, title, URL, target, draft or ready, checks with the failed ones, review decision, unresolved threads (the URL alone when the feed does not have it); the commits on the branch not in `<remote>/<base>` and the uncommitted files (the first 20 of each); the Kelta MCP tools the session lists (`tools/list`, built from the registered tools); `claude.append_system_prompt`. It is rewritten on every launch (start, Resume, Dormant restore, `--continue` fallback), so a resumed Claude reads the current state, and the prompts need not repeat it.
   5. Create tab `KEY title` with the template layout (default Claude | nvim, 50/50). If `worktree.setup` is non-empty: a visible `setup` pane below; when `worktree.setup_blocking=true`, Claude waits for exit 0 (failure → Retry / Continue anyway).
   6. Spawn editor (`nvim --listen <runtime>/s/<sid8>/nvim.sock .`) and Claude:
      `claude --session-id <uuid> -n "SHOP-142 Rate-limit login" --model <m> --effort <e> --permission-mode <p> --settings <run>/claude-settings.json --mcp-config <run>/mcp.json --allowedTools "mcp__kelta__*" --append-system-prompt-file <run>/context.md "<prompt>"` (cwd = worktree).
   7. Tracker side effects **after** sessions are up, in parallel, each non-fatal: assign me; transition to `status_map.start` (resolved by category or name from `transitions()`; `NeedsFields` → small form built from the field errors, or "Open in browser"); optional comment.
   8. Persist WorkItem; emit `ticket.started`, `worktree.created`; ticket card shows a "local work" badge.
3. **While working:** Claude status in pane header/tab/rail; notifications when Claude needs input or finishes while its pane is hidden or the window unfocused. Claude edits → nvim `:checktime` (`editor.follow_claude_edits = reload`; `open` also opens the file without stealing focus). `Mod+Shift+L` in nvim sends the visual selection to Claude as `@path#Lx-y` (bracketed paste when enabled). Claude can call MCP tools tied to its work item (`get_ticket`, `transition_ticket`, `add_ticket_comment`, `open_in_editor`, `create_pr`, `get_review_feedback`, `add_review_comment`, `notify`, `ask`) and board-wide ones (`list_tickets` with `project`, `view`, `status`, `assignee`, `label` and `tag` filters, `get_ticket_by_key`, `list_review_requests`, `claim_ticket`, `report_progress`, `release_ticket`, `link_pr` (its `status`, a role `start` / `review` / `done` or a status name, moves the ticket after linking, and needs `claude.mcp_board_writes`), and with `claude.mcp_board_writes` `transition_ticket_by_key`, `comment_ticket_by_key`, `update_ticket_body`, `close_ticket`, `move_ticket_step`); the setup tools (`get_setup`, `add_project`, `set_setting`, `test_account`, `request_token`) configure Kelta itself, as in "Set up with Claude" (`claude.setup`, onboarding and palette).
4. **Desk header** (above the work tab's panes, §1) and **Story panel** (`Mod+I`): the header names the item, its stage and the phase's one primary action, with the **Actions** menu (`Mod+.`); the Story panel holds the ticket status (click → Move to…), Claude, the changes, the PR and the start log (FLOW §2.4). The menu: Ship / Push, Review diff, Fix with Claude, Rebase, Open ticket, Open PR, Merge when ready, Mark ready / Convert to draft, Park, Finish and the other steps of FLOW §2.5.
5. **Ship** (FLOW §4.5): title (`work.pr.title_template`, `{ticket.key}: {ticket.title}`), description (`work.pr.body_template`: ticket link, `Closes #n` for GitHub issues) and a Draft switch (`work.pr.draft`); refused while Claude is working or when no commit is ahead. It runs `git push -u origin <branch>` in a transient visible pane (credential prompts work) → if a PR already exists for the branch (Claude may have used `gh`), link it; else create it via CodeHost → transition the ticket to `status_map.review` (else `work.on_pr.transition_to`), optional comment with the PR URL (`work.on_pr.comment`) → `pr.created`. With a PR open, the same key is a plain Push.
6. **Finish** (offered when PR merged or ticket Done, or manually): kill sessions (confirm if Claude is working), `git worktree remove` (refused if dirty or unpushed unless **Force**), optionally delete local branch, transition to `status_map.done` if configured, mark WorkItem finished. `git worktree prune` runs at app start.
7. **Resume:** opening the ticket again or the WorkItem from the palette focuses or recreates its tab; Dormant sessions respawn on show (`claude --resume <uuid>`, fallback `--continue`).

### 3.2 Standalone session (no ticket)
`Mod+T` → picker: template (the enabled `session_templates`, five by default, plus plugin templates and any tool), project (active, any open, Home), cwd (project repos, existing worktrees, recent dirs, browse), placement (new tab / split right / split down). Spawned immediately (no worktree, no tracker call). Claude sessions still get hooks + their own MCP (`--mcp-config` → `/mcp/<sid>` when `claude.mcp` is on, so the session tools work; `get_ticket` returns "no ticket linked"). **New work item** (`work.new`, `Mod+Shift+N`, `kelta-ctl start --task`) = the start-work flow with a typed task instead of a ticket: a scratch work item on a `wip/<slug>` branch (`work.scratch_branch_template`), tracker steps skipped (FLOW §4.3). A scratch item gets a ticket later with Work: Link to ticket (`work.link`), or files one with Work: Create ticket (`work.create_ticket`).

### 3.3 PR / MR review list and actions
- **Pull requests** pane per project (repos bound to the project) or aggregated (Inbox, all accounts, "Other" for unbound repos). One list in sections (#401): *Asked of you* (review requests; one line when empty), *Team, needs a reviewer* (Team's PRs neither mine nor asked of me, not drafts), *Team drafts* (folded), *Yours, as reviewers see them* (my PRs); each PR once. Within a section a PR whose base is another listed PR's head follows it with an elbow ("merges into #N", "base of a stack of N"). Row: number, title, failing / running checks, the review state in words (from `Review.reviewers` and `waiting_on`) or Draft, author (not on mine); the change map (`Review.files` by path into code, tests, config, other; linear up to 2k lines, then cut; "1.3k lines, 49 files"); the open age (`created_at`), amber past 14 days on team PRs. The brief beside it (`Brief`, as the Queue): title, author, open age, checks, branch → base; Review locally (Go to work item on mine), Approve, Comment, the rest behind `.`; review status per reviewer; *Before merging* (the description's section under a heading naming before merging, deploy, migrations or rollout); change map, description, files grouped by area biggest first. Filters: text, tag, repo (team requests follow `reviews.include_team_requests`).
- **Team** (#241): the open PRs of the repos bound to the projects some ticket source feeds (`CodeHost::list_open`; GitHub chunks the repos into searches of at most 256 characters in one GraphQL request, GitLab / Gitea / Bitbucket list each repo). In a project's pane it covers that project's repos and shows only when a source feeds the project; "Other projects" never count. Everyone's PRs, drafts included (folded into *Team drafts*); the ones asked of me or mine show in their own sections. `reviews.repos_allow` / `repos_deny` apply. Team is polled only while a visible Pull requests pane or the rail's view shows it, raises no notification or badge, and never reads the requested feed's gate. A host that cannot list team PRs (a plugin without `codehost.list_open`) shows an account error. Without one: "No ticket source feeds a project with a repository yet" (Add a ticket source).
- **Waiting on** (#240): every row, in every tab, carries `ReviewItem.waiting`, computed in core with identities merged across trackers and code hosts (§3.4a): the reviewers still asked (a review wait, from `Review.waiting_on`, now filled for review requests too on GitHub and GitLab) and the author when changes were requested on the current head (`Review.author_to_act`; GitLab approximates, it ties no review to a commit). The chip reads `waiting on Anna · 26h` or `waiting on Anna +2`, amber past `reviews.sla_hours` on My PRs only; a request row shows `waiting on Bob (author)` and no chip when it waits only on me. Nudging stays on My PRs (Mine).
- **Split view** (as Tickets, §3.4b): in a Pull requests pane 720px or wider (the rail's view and a project's tab) the selected PR's detail shows in a column on the right; selecting a row loads it and marks it seen. `Space` toggles it, `Enter` focuses it, `Esc` returns to the list, `Shift+Enter` opens the standalone detail in the PR's project (also what `Enter` does in a narrow pane). The column is the same `ReviewDetailPane`, run in the PR's first project (else the active one).
- **Cross links in the rail's views:** `p` on a ticket in Tickets switches to Pull requests with that PR selected, its section opened; a PR in neither list, or on an unbound code host, opens as before (standalone detail, or the browser). A PR's linked-ticket badge switches to Tickets with that ticket selected when the view has it loaded, else it searches and opens the ticket in its project as before.
- **Keys in the list:** `j` `k` move, `Enter` focuses the detail, `Shift+Enter` opens it standalone, `Space` splits, `/` filters, `R` refreshes, `1` `2` `3` switch tab, `G` groups Team, `o` browser, `s` Review locally, `t` Tags (#349), `w` Run workflow (#355, `[[workflows]]` with `on = "pr"`; opens in a background Claude tab in the PR's worktree or repo). On My PRs only: `n` nudge (Comment ping or Re-request review), `M` Merge when ready (a PR with a work item), `d` Mark ready for review / Convert to draft (#353; asks before marking ready; not offered on a plugin code host).
- **Detail:** sanitized description, reviewers, checks summary, file list (+/− counts), local tags. Actions: **Approve** (`a`; sends the shown `head_sha`; stale → "PR changed, refresh"), **Comment** (`m`), **Request changes** (`c`; GitLab: comment + optional unapprove), **Review locally** (`s`), **Open in browser** (`o`), then **More**: **Tags** (`t`), **Run workflow** (`w`), **Refresh** (`R`); one row (#384). On my own PR there is no Approve, Request changes or Comment (`a` `c` `m` do nothing): `f` Fix with Claude, `g` Review locally, `d` draft.
- **Review locally** (`work_plan` with `Review` source → same sheet): fetch `pull/<n>/head:kelta/pr-<n>` (GitHub) / `merge-requests/<iid>/head:kelta/mr-<iid>` (GitLab) / `pull/<n>/head:kelta/pr-<n>` (Gitea) / the source branch (Bitbucket Cloud, which exposes no PR refs) → worktree `<root>/review-<n>` → template `review` (Claude with profile `review`, `--permission-mode plan`, prompt from `claude.prompt_templates.review`; nvim with `editor.review_args`, e.g. `-c "DiffviewOpen origin/{base}...HEAD"`; shell with `git diff --stat origin/<base>...`).
- Rows refresh on window focus through the list query (one request, also brings back PRs pushed after my review, badge "Updated since your review"), never through `get` on each row.
- New review requests detected via `seen_reviews` (never on the first poll after start) → desktop notification (toggle) + rail/Inbox badge.

### 3.4 Move ticket status
- **Status picker:** one component (`StatusPicker`) for every place a status changes: list `m`, the detail header, the Story panel's Ticket section and the palette. Fed by `tracker_transitions` (cached per ticket and current status for the focused polling interval, dropped when the ticket is written): the ticket's own workflow as a line of native status names, then its legal transitions numbered `1`-`9` (`m` `2` moves), fuzzy filter, a needs-fields form, and on a conflict or tracker error the tracker's message with Open in browser.
- **Several tickets:** `x` marks the current ticket, `Shift+j` / `Shift+k` extend, `m` moves them all. The picker offers the transitions every marked ticket can take, matched by target status name (transition ids differ between workflows); a ticket already in that status is skipped.
- **Board:** columns from `tracker_columns {source_id}` (the source's `tracker.columns` override; default by status category: To do / In progress / In review / Done). Drag a card (or select + `m`) → `tracker_move {ticket, column_id, source_id?}`: resolves column → transition by category or names; several candidates → small picker; none → toast "No transition to <column> — Open in browser"; `NeedsFields` → field form or browser. Optimistic move with rollback on error.
- **Detail:** the status chip opens the picker; assign (Me / none), comment box (Markdown). Layout and actions in §3.4b.
- **Palette:** "Move SHOP-142 to…".
- Provider semantics: Jira transitions; Redmine `allowed_statuses`; GitHub Projects v2 Status (or open/closed); GitLab scoped labels + close/reopen; Linear workflow states of the ticket's team; Gitea open/closed.

### 3.4a Choose ticket sources and who
- **Boards are global.** A board (account, views, columns, pipeline, routes) is a `[[sources]]` entry of the global config (SETTINGS §2) that feeds zero or more projects; projects do not own it. A board shared by several projects is configured once. `Scope::Project` lists the boards feeding the project, `Scope::Source` one board, `Scope::All` every board, including boards that feed no project or only closed ones. A ticket's projects are its board's `projects`. The former `[project.tracker]` blocks move there at startup (SETTINGS §3).
- **Pipeline** (#460, config only: nothing runs the steps yet, #461): a source's `tracker.pipeline` (else the global `work.pipeline`) lists its tickets' steps: `id`, `label`, `enter` (events `work_started`, `pr_opened`, `pr_ready`, `review_requested`, `changes_requested`, `approved`, `merged`, or a status `{ status = { name = "PO Review" } }` / `{ status = { category = "in_review" } }`; empty = manual only), optional `transition_to` and `comment`. Unset, the steps come from `status_map` and `work.on_*`: Implementing (`work_started`, `on_start` / `status_map.start`), PR (`pr_opened`, `on_pr` / `status_map.review`), Review (`pr_ready`, `review_requested`), Merge (`approved`), Done (`merged`, `on_merge` / `status_map.done`). Step ids must be non-empty and unique and a status trigger must name a status (a file error at the key's path). `status_map` and the `transition_to` / `comment` of `work.on_*` are deprecated: a settings warning, still read as the fallback. SETTINGS §2 lists the keys.
- A **source** is a tracker view: a Jira board or filter, a Redmine project or query, a GitHub repo or Projects v2 board, a GitLab project, a Linear team, a Gitea repo. A project binds any number of them, each optionally from another account (`views[].account`; none = the binding account), so one project can mix Jira and GitHub tickets. Board mode and `tracker_columns` stay tied to the binding account.
- **Add a source** from the Tickets toolbar (source menu, `v`, then "Add source…") or Settings → Sources (Add source): pick an account, search, press `Enter` on a hit (`tracker_sources` lists boards, projects, filters, teams, repos). A provider without discovery says so and offers the TOML.
- The Tickets pane, the Queue and the palette with no source chosen show **every source of the project**, one first page each, deduped by account and ticket key; Load more pages every source at once (one cursor per source). The source menu narrows the pane to one.
- Ticket search (palette, pickers: `tracker_search`) asks each source's tracker (`Tracker::search`: Jira `text ~`, Linear title/description, GitHub/GitLab/Gitea search, Redmine `subject ~`), not the cached page; a tracker without search, or a failed search, filters its cached first page.
- **Who** tabs: *Mine*, *Unassigned*, *Team* (keys `1` `2` `3`; the wire value of Team stays `Who::Anyone`, so saved panes keep working). The choice is saved with the pane.
- **Current iteration** (per source toggle) keeps the open sprint (Jira), active cycle (Linear), current iteration (GitHub Projects v2), started milestone (GitLab) or the project's next open version (Redmine). Gitea has none.
- Statuses show the tracker's own names. The category (To do, In progress, In review, Done) only orders and colours them, so Backlog, Triage, QA or Blocked appear as they are; a source's `status_colors` recolours a status chip (SETTINGS §2). Done starts collapsed.
- The **team** is derived from data already polled, with no config: the assignees and reporters of the scope's Team (`Who::Anyone`) ticket caches, and the authors and requested reviewers of the cached review lists of the scope's code-host accounts (`TicketPage.people`, cache only, no provider call). Core merges identities, each rule exact and in order: every account's `me()` is "You"; a tracker and a code host on the same base URL merge on the same login (ignoring case); two identities with the same email (Jira `emailAddress`, GitHub public email) merge; otherwise they stay apart, `matched: false`. Display names never merge people. A ticket's `waiting` (`TicketItem.waiting`) lists its main open PR's waits, then *Assigned* (ticket not done, assignee not me); the Tickets row shows the chip next to the PR chip, none for an assignment alone (the avatar says it). Nudging stays on My PRs.
- The **person** control narrows the list to one team person with a tracker identity (client-side, `TicketPage.people`; unmatched people are marked, and a person id saved before team people still filters; choosing one implies Team). Saved with the pane (`PaneContent::Tickets.person`).
- Group by (`G` cycles, saved with the pane): **Flow** (default), Status, Priority, Sprint, Assignee, Source, Parent (epic or parent issue, no parent last; #350), None. Flow: *Doing* (work item active or in-progress status), *Waiting* (Claude needs input, review requested or required, CI red, or a status named blocked / on hold / waiting), *Ready* (to do, not started), *Backlog* (backlog / triage / icebox or an unknown status), *Done* (last 7 days only: a source with no status filter also fetches the first page of its closed tickets and keeps those done in the last 7 days). Sort within groups (saved): Priority, Updated, Age in status, Key.
- Each ticket carries `priority_rank` (0 = highest), `status_since` (RFC 3339; Jira `statuscategorychangedate`, Linear `startedAt`, other providers fall back to `updated_at`), `sprint`, `estimate` and `due`. A ticket not done shows an age badge from 7 days in its status, in place of the updated time (text tint only, `--k-warn` from 14, `--k-danger` from 21). The Doing header turns `--k-warn` above `tickets.wip_limit` (default 3); nothing is blocked.
- Sprint: a chip on every row unless grouped by sprint, quick filter `f` `s` (the active sprint, client-side), and the per-source `current_iteration` stays as the server-side limit.
- A row shows the linked pull request and its CI state: the work item's PR first, then any polled review whose `linked_tickets` name the ticket (`TicketItem.prs`). `p` opens it in Kelta's review detail when the repo is bound to a code host account, else the browser; `P` always the browser; several PRs open a small picker.

### 3.4b Ticket detail and split view
- In the Tickets pane (list, 720px or wider) the selected ticket's detail shows in a column on the right. `Space` toggles it, `Enter` focuses it, `Esc` returns to the list, `Shift+Enter` opens the standalone detail pane (also what `Enter` does in a narrow pane). Both use the same `TicketDetail` body.
- Top to bottom (#400): key, epic name, title; status chip (status picker), type and points, the situation in one line; action bar (Start/Resume is always the primary; the row is Start, Move, Comment, plus Open PR only when a PR is linked); the latest comment and the spec's open section (a heading named Open questions, Missing, To clarify, Questions, TBD); pull requests (title, state, CI, review, branch; nothing when none); description as one foldable section per heading (raw ticket links as key and title chips, Given / When / Then laid out, task-list checkboxes read-only); the fields that have a value (assignee, priority, sprint, due, the source's fields, labels, updated); comments (last 20, compose box, `Mod+Enter` posts).
- Action bar: Move `m`, Start / Resume work `s`, Open PR `p`, Assign `a` (Unassign `A` once assigned), Comment `c`, Block / Unblock `b` (the source's `blocked` marker, SETTINGS §2), Refine `r`, Run workflow `w`, Copy branch `y`, Open in browser `o`, Tags `t`, Start another PR `N` (once the ticket has work, FLOW §2.1; with several items Resume work opens a picker), Next step `e`, Move to step… `E` (once the ticket has work, FLOW §4.9) (the bar shows Start / Resume as the primary, then Move and Comment, and Open PR only when a PR is linked, each with its key; Assign to me and the rest are under More, `Mod+.`). `u` picks an assignee, `!` a priority, `R` reloads. Each carries its key; an action that cannot run stays visible and dimmed with its reason as the tooltip and as the toast when its key is pressed: the tracker lacks the capability (`TrackerCaps.assign`, `comment`, `block`, carried on `TicketItem.caps` / `TicketDetail.caps`), no PR is linked, no branch yet. The selected or hovered row (and a row with focus inside) shows a compact Move / PR / Start.
- Sub-tasks (`TicketDetail.children`: Jira subtasks, Linear children, GitHub sub-issues, GitLab child items, Redmine children; Gitea has none) list under the pull requests with their status chip. `Enter` on one opens its detail, `s` starts work on it (`S` with no sheet).
- **Refine with Claude** (`r`): a one-shot `claude -p` in the project's primary repo (its Claude settings: binary, default profile model and effort, env; edits disallowed) reads the ticket body and recent comments on stdin, with MCP `get_ticket` resolving to the ticket for that run, and proposes acceptance criteria, open questions and an optional split into sub-tasks. The proposal shows as a preview in the detail: Post as comment, Copy, Discard. A kept proposal's acceptance criteria are appended to Claude's first prompt when work starts on the ticket. Editing the description and creating sub-tasks from the proposal are not offered (Claude can rewrite a body through MCP `update_ticket_body`).
- **Run workflow…** (`w`, also `w` on a list row and the palette's `Run workflow on <key>…`): a picker of the saved Claude workflows (`*.js` with an `export const meta` in the project's primary repo `.claude/workflows/` or `~/.claude/workflows/`; name, description, `repo` / `home`). A held ticket is refused with its holder. Off with its reason when the ticket has no project or no workflow is found.
- Not in the detail yet: lifecycle lamp.

### 3.4c Local tags (#349)
- Personal reminders ("retest on staging", "ping the PO") on tickets and pull requests, never sent to a tracker or code host: one `ui_state` value in Kelta's store (`tags_get` / `tags_set`, `LocalTags`), so they survive a restart and follow an item across views and projects (keyed `account:key` and `account:repo#number`).
- Settings → Tags defines them (name, theme colour or hex). A rename keeps the tag on its items; Delete asks first, then takes it off everything.
- `t` on a Tickets or Pull requests row, a ticket row's tag button, the ticket detail's More menu (`t`) and the review detail's Tags button (`t`) put a tag on or take it off. Rows (Tickets, Pull requests and the Queue), board cards and both details show the tags as chips. Each change is applied to the freshly stored set, so another window's tags are never overwritten. The Tickets and Reviews toolbars show one chip per tag the list carries, with its count; picking one narrows the list (per pane, not saved).
- MCP `list_tickets` takes a `tag` filter (read-only).

### 3.5 Open a tool
Tools are buttons for terminal programs (`kind = "pty"`, e.g. lazygit), apps launched beside Kelta (`kind = "external"`, e.g. `open -a Fork .`) and web tools. They are added from Settings → Tools (**Add tool**: Terminal or App, a name, a command line or an application, an optional key with conflict warnings) or `[[tools]]` in a config file (docs/user/tools.md). Tools are opened from the palette ("Open tool: lazydocker"), `Cmd+Alt+1..9` on macOS (tool N in config order), a tool's keybinding, or a trigger; the rail has no Tools section (#412). Tools are defined once, in the global settings, and open where you are: in a project, in that project with its focused work item; in a global view (Tickets, Now, Reviews) or Home, in Home with no work item. A terminal tool opens as a pane of the current tab, split off the focused pane and zoomed, in the tab's worktree or the project folder; its key or `Esc` `Esc` closes the pane (the previous layout comes back, the session keeps running) and the key brings it back zoomed while it runs. There is no tool tab. A tool's `scope` sets its instances: `work` (default) one per work item, `project` and `user` one per project for a terminal tool; a web tool keeps its own place (`work` at its placement, `project` one tab per project, `user` one tab in Home). `tools.open` picks the host before switching anything, then opens the instance or brings it to the current tab. A tool whose templates use `{project.*}` or `{repo.*}` (`needs_project`) opened with no project in context shows a project picker (every project but Home, open or closed; a closed one is opened first; `Esc` opens nothing) and opens in the picked project with no work item. The palette adds "Open <label> for project…" for those tools, which always shows the picker. `tool_open` → PTY tools become sessions (`kind = Tool`, cwd per tool template, exit banner with **Relaunch**, `close_on_exit` option); web tools start their server (if any), wait for readiness from stdout (no polling), then open a Web pane. Embed `auto`: iframe; if a HEAD probe sees `X-Frame-Options`/`frame-ancestors` → local proxy that strips them (WebSocket passthrough); failure → **Open in browser** button. Web tool processes stop when the pane/tab closes (`lifecycle`), or with the project. Missing binary → empty state with `install_hint` and "Check again".

### 3.6 Plugin screens
Plugins contribute screens opened from palette/commands/keybindings/triggers into a tab or pane. A screen is a sandboxed iframe created when shown and destroyed when hidden (unless `keep_alive`, listed in Settings → Performance, which keeps it while its pane stays mounted; a tab or project switch still destroys it). Install from directory / git URL / tarball shows the manifest, requested permissions in plain words and the SHA-256; grants stored in app state; updates requesting new permissions re-prompt. Disabled plugins contribute nothing.

## 4. Keyboard shortcuts

Principles: Linux follows the macOS set with Cmd → Ctrl (`Mod` = **Cmd** on macOS, **Ctrl** on Linux; derived in the catalog, with explicit Linux chords only where Cmd+Ctrl has no twin and for terminal copy / paste). In a focused terminal on Linux a plain Ctrl+letter goes to the terminal (`keys.linux_terminal = "terminal_first"`, the default; `kelta_first` lets Kelta win), so each default plain Ctrl+letter also has a Ctrl+Shift+letter twin unless another action's Mod+Shift+letter takes it (`pane.split_right`, `attention.next`, `rail.toggle`, `terminal.search`: prefix or palette from a terminal). Kelta never takes Alt/Meta+anything, Shift+Tab, Ctrl+Space, Ctrl+\\ or Super chords from the terminal; Ctrl+Alt chords are the Cmd+Opt twins (the window manager may take Ctrl+Alt+arrows). Ctrl+C in a terminal is always SIGINT; copy / paste are Ctrl+Shift+C / V. On macOS Cmd never reaches the PTY except Cmd+C/V handled by Kelta. A configurable **app-prefix key** (tmux-style, default `ctrl+shift+space`, `keys.prefix`; `"off"` disables) followed by one key within `keys.prefix_timeout_ms` (1000) reaches every action. All bindings are rebindable in `[keys.bindings]`; the keybinding editor flags conflicts with the reserved list and with other bindings. Letters and punctuation match the character the active layout types (AZERTY `ctrl+w` is the key labelled W; punctuation uses the key's unshifted character, learned from plain presses); digits and named keys match physical keys (`KeyboardEvent.code`) so layouts don't break digits, and non-Latin layouts fall back to the QWERTY position.

## 7. Notifications

Desktop notifications (`tauri-plugin-notification`) fire only when the related pane is not visible or the window is unfocused (`notifications.only_when_unfocused`), outside `quiet_hours`: Claude needs input, Claude done, new review request, CI failed on my PR, my PR approved / changes requested, bell in a background project. Click → focus window, project, tab and pane (macOS: focus app if click routing unsupported). Dock badge (macOS) / urgency hint (Linux) = number of sessions needing input.

## 8. Platform behaviour

- **Linux:** Ubuntu 24.04+ primary (deb), AppImage best-effort, Arch/Fedora best-effort.
