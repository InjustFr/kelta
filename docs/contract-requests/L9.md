# L9 (UI work views): deviations and contract requests

Scope: `ui/src/views/{tickets,reviews,inbox,work}/**`, `ui/tests/e2e/work/**`. Nothing outside those paths was edited.

## Requests (scaffold-owned files)

1. **Skip a failed start-work step.** SPEC §3.1 / ARCH §12.1 want `Retry`/`Skip` per failed saga step, but the command catalogue only has `work_retry_step`. The sheet therefore shows only `Retry` (the `Skip` button is hidden until the command exists). Request: a `work_skip_step {id, step}` command (or a `skip: bool` argument on `work_retry_step`) that marks the step `skipped` in `work_steps` and resumes the saga.
2. **Review list filters.** SPEC §3.3 lists the filters "include drafts, team requests, repo". `review_list` takes only `{scope, kind, refresh}`, and `Review` has no "requested through a team" flag. The pane filters drafts and repo client-side; team requests stay governed by `reviews.include_team_requests` in the settings. Request: add `include_drafts` / `include_team` to `review_list` (or a `team_request: bool` on `Review`) if a per-view toggle is wanted.
3. **Error `detail` shapes.** The views parse the shapes ARCH §3 documents and are tolerant of variants: `NeedsFields` `detail.fields` as strings or `{id, name, required, allowed_values}` (plus an optional `detail.transition_id`, otherwise the transition is resolved through `tracker_transitions` by target name/category); ambiguous `tracker_move` as `Conflict` with `detail.candidates` (`Transition[]` or `{id, name}`); "no transition" as `NotFound`/`Unsupported`; `Dirty` with `detail.files: string[]` (an unpushed-only refusal has an empty list and its message is shown). Field values are submitted as plain strings (`fields: {id: "value"}`); providers that need structured values (Jira `{name: ...}`) must accept strings or document the shape.
4. **Board outside a single project.** `tracker_columns` is per project, so the board is offered only for a project scope with a tracker. The aggregated scope (`all`) stays list-only.
5. **Production build and chunk measurement.** `src/main.ts` only references `registry` under `VITE_IPC=mock`, so a normal `vite build` contains none of the lazy views until the shell (L2) imports the registry. The 120 KB gz budget was checked with `VITE_IPC=mock vite build`: the largest L9 chunk (`TicketsPane`) is 5.7 KB gz, the shared `common` chunk 7.3 KB gz.
6. **Toast action.** The "No transition" toast carries `{command: "tickets.open_in_browser", args: {url}}`, an action registered by `views/tickets/actions.ts` (not in the ActionId catalog). The shell's toast host must dispatch `toast.action.command` through `dispatch()` (the harness does).

## Notes for the merge owner

- `work.start` acts on the ticket selected in the focused ticket view (`views/work/selection.svelte.ts`), or on `args.ticket` / `args.project_id`. The key manager should dispatch it with the `ticket_views` context only.
- The panes persist their view switcher and list/board mode into the layout (`replacePaneContent`), so they survive restarts.
- The e2e harness (`ui/tests/e2e/work/harness/`) hosts panes, the sheet registry and toasts because the shell is still L2's stub; it is served by the Vite dev server and does not ship in the app.
- Branch validation in the plan sheet approximates `git check-ref-format`; the backend remains authoritative.

## Ticket workbench (WP0): contract change

The contract freeze is lifted for the ticket workbench. Recorded here:

- `Who` = `mine | unassigned | anyone`. `TrackerView` gains `who: Option<Who>` (`None` keeps the provider fields
  `assigned_to`, `scope`, `jql` as they are), `current_iteration: bool` and `account: Option<AccountId>`
  (`None` = `binding.account`). All default, so existing project TOML still parses.
- `PaneContent::Tickets` gains `who: Option<Who>` (serde default, so saved layouts still load).
- `Tracker::sources(query) -> Vec<SourceHit>` (`{kind, label, detail, view}`), default `Unsupported`; KPP
  plugins compile unchanged.
- Commands: `tracker_list` gains `who` (overrides `view.who`; the cache key separates per who),
  `tracker_move` gains `project_id` (picks the columns; `None` = the project bound to the ticket's account),
  new `tracker_sources {account_id, query}`.
- `TicketItem.view_ids`: ids of the binding views (sources) that returned the ticket (union-merged like
  `project_ids`).
- `SourceHit.view.account` is stamped by the core in `tracker_sources`; providers leave it `None`. An
  `Unsupported` from `sources()` does not change the account status.
- `tracker_move(project_id = None)` resolves the project whose binding account or one of whose views' `account`
  is the ticket's account. Panes pass `project_id` anyway (board: the pane's project; menu:
  `item.project_ids[0]`).
- Union of a project's views when `view_id` is `None` is not in WP0 (WP2). The mock already models it for
  done tickets (kept when `view_id` is null).

Decisions for the downstream packages:

- Now = `tracker_list(All, null, who='mine')`; WP2 changes the scheduler's `PaneContent::Inbox` subscription to
  `Some(Who::Mine)` so the background refresh hits the same cache key. A tickets pane loads with
  `who == content.who` (the persisted value, which the subscription is keyed on); other who tabs loaded for
  counts are served from cache.
- When the effective `who` is `Some`, providers ignore `assigned_to` and `scope` (WP1); `jql` is sent as is.
  The onboarding `defaultView` (WP4) emits `who: 'mine'` and drops the assignee clause from `jql` and the
  `assigned_to`/`scope` values; old configs keep working through `who: None`.
- No capability flag for current iteration: WP4 shows the toggle for every kind except `gitea`.
- Who-tab counts: one `tracker_list` per who; omit a count when unknown.
- `MoveController` / `MoveDialogs` (`ui/src/views/tickets/move.svelte.ts`) keep their import path and API
  (`moveToColumn(ticket, column, projectId)`) while WP3 and WP5 run in parallel.
