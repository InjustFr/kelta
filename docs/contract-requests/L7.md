# L7 — Server, hooks, MCP, kelta-ctl: deviations and requests

## Deviations

1. **MCP transport is the hand-rolled JSON-RPC fallback, not rmcp.** BUILD_PLAN §4 L7 allows it ("fallback hand-rolled JSON-RPC"). rmcp 3.5.1's `StreamableHttpService` spawns per-session tasks, keeps legacy MCP sessions alive and sends SSE keep-alive pings on a periodic timer, which runs against BUILD_PLAN §1.5 (no periodic timers outside allowlisted modules). `/mcp/<sid>` is a stateless Streamable-HTTP subset: `POST` with one JSON-RPC message (or a batch) → `application/json` response; notifications/responses → `202`; `GET`/`DELETE` → `405` (no server stream, no `Mcp-Session-Id`). Methods: `initialize` (negotiates `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`), `ping`, `tools/list`, `tools/call`, empty `resources/list` / `prompts/list`. **Request:** the merge owner may drop `rmcp` from `crates/kelta-server/Cargo.toml` (declared, now unused) to save compile time; nothing else depends on it. Gate C1 must confirm Claude Code connects (it accepts JSON responses to POST per the Streamable HTTP spec).
2. **Additive public method `Server::http_port() -> Option<u16>`** (port of the running HTTP server, `None` when stopped). Used by tests to assert "not running without consumers"; useful for diagnostics. No existing signature changed.
3. **Peer uid via tokio, not rustix.** rustix 1.1.5 only has `socket_peercred` (Linux, `SO_PEERCRED`) and no `getpeereid`; `tokio::net::UnixStream::peer_cred()` uses `SO_PEERCRED` on Linux and `getpeereid` on macOS. Our own uid (`getuid`) comes from rustix. Directory owner/mode use std `MetadataExt`.
4. **No Kelta-generated `claude-settings.json` fixture exists in proto.** Settings generation belongs to L6 (Claude launcher). The end-to-end test (`crates/kelta-server/tests/it/e2e_fake_claude.rs`) builds the settings exactly as PLUGINS §8 specifies from `kelta_proto::hooks::names` (events, `NOTIFICATION_MATCHER`, `EDIT_TOOLS_MATCHER`, POSIX-quoted `'<kelta-ctl>' hook`, `async` except `SessionEnd`). **Request:** a shared generator (e.g. `kelta_proto::hooks::claude_settings(ctl_path, transport)`) or a generated fixture so L6 and L7 test against the same document.
5. **`kelta-ctl version`** prints `{"ctl": "<version>", "app": <server version result | null>}` and exits 0 even when Kelta is not running (an `error` field explains why `app` is null); `--version` prints plain text. `Version` is answered by kelta-server itself (`{"version", "protocol"}`), not forwarded to `CoreApi::ctl`.
6. **ctl dispatch:** `hook` is handled in kelta-server (token check → `hooks::map` → `session_apply_hook` + bus `claude.hook` / `claude.file_edited`); `emit` is validated (`custom.<non-empty>`) and then forwarded to `CoreApi::ctl` like every other command (core publishes the event). Paths (`open`, `trust`, `new --cwd`, `editor-open`, local `plugin install` sources) are made absolute by kelta-ctl against its cwd. `editor-open a.rs:12` is parsed as line 12 unless `a.rs:12` itself exists.
7. **kelta-ctl exit codes:** `0` success, `1` server error or Kelta not running (JSON error on stderr), `2` usage error. `hook` always `0` and silent.
8. **Hook HTTP transport** (`POST /hook/<sid>`) answers an empty `200` after authentication (bad JSON → `400`), so Claude never receives a decision from Kelta.
9. **`claude.hook` bus payload:** `{event, matcher_value, payload}` where `matcher_value` is `notification_type` (Notification), `tool_name` (PostToolUse/PermissionRequest/PreToolUse), `source` (SessionStart) or `reason` (SessionEnd). Claude's payload never contains transcript contents (only `transcript_path`), so it is passed through unchanged.
10. **MCP `transition_ticket({to})`** matches, in order: transition id, transition name, target status name (case-insensitive), then status category (`todo`, `in_progress`, `in_review`, `done`). Transitions that need fields return a tool error asking the user to move the ticket in the UI. It calls the `Tracker` directly (CoreApi has no ticket-transition method). The MCP tools publish `ticket.transitioned` (`{ticket, from, to}`; `from` comes from a `Tracker::get` before the move, null if that fails) and `ticket.commented` (`{ticket}`) themselves via `CoreApi::publish`, with session and project context. **No tickets cache invalidation happens. Request:** add `CoreApi::ticket_transition` / `ticket_comment` (core-owned events + cache invalidation) and switch the MCP tools to them (then drop the local publish).
11. **MCP `open_in_editor`** resolves relative paths against the session cwd and targets the session's work item when it has one (`EditorTarget::WorkItem`), else `EditorTarget::Session`. `list_review_requests` uses `review_list(Scope::All, ReviewKind::ReviewRequested)`. `notify` uses the session name as title, `Urgency::Normal`.
12. **ctl connection limits:** request line cap `CTL_MAX_LINE` (oversized → `invalid_argument` "frame too large", connection closed); a connection idle for 30 s without a complete line is closed (one-shot deadline per read). An existing live socket at `<runtime>/ctl.sock` makes `start_ctl` fail with `Conflict`; a stale one is replaced. Dropping `Server` aborts the accept task, removes the socket and stops the HTTP server.

## Acceptance notes

- Peer-uid rejection cannot be exercised in a test without a second uid; it is enforced on every accepted connection before any byte is read (`ctl.rs::serve_conn`).
- `kelta-ctl` sizes on macOS arm64: `--profile release-ctl` 353 KB (stripped), `--release` + `strip` 475 KB.
- Cold `kelta-ctl hook` on macOS (no socket, includes process spawn): ~30 ms wall per run in a shell loop, dominated by macOS exec overhead (informational).
