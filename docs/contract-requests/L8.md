# L8 — contract requests and deviations

Lane L8 (plugins, tools, triggers, screen sandbox, plugin SDK). Each item: what deviates, the local workaround, and what the merge owner should decide.

## Requests to other lanes

1. **Start the plugin host at startup (L3).** `PluginHost::start()` subscribes the trigger engine to the bus; `Core::start` does not call it, so the desktop commands start it lazily (every `plugin`/`tool`/`trigger` command calls `plugin_host(&core)`, which wires and starts it). Workaround in L8 paths: `ui/src/lib/plugin-host/boot.svelte.ts` loads `plugin_list` once projects are loaded, which starts the engine right after launch. Request: `Core::start` calls `plugins().wire(..)` + `plugins().start()` so triggers run even without a UI.
2. **Host services not in `CoreApi` (L3).** `PluginHost::wire(Wiring { ui, settings, settings_writer })` is an addition: the UI bridge (`plugin.event` relay, web tool handles, focus), `SettingsSource` (project configs for `projects.list`) and a Global-layer writer for the SDK's `settings.set`. Wired from `apps/desktop/src-tauri/src/commands/plugin.rs` on first use. Request: wire it in `Core::start` instead (same struct).
3. **Web tool state for panes (proto/L2).** `PaneContent::Web` only carries `tool_instance_id` and there is no command to read a running web tool's URL, embed mode or log. Workaround: the host relays `UiEvent::PluginEvent` with `instance_id = <tool instance id>`: `kelta.tool_handle` `{handle, tool_id, label, project_id, lifecycle}` on open and `kelta.tool_exited` `{code, log}` on exit; the UI caches them (`ui/src/lib/plugin-host/web.svelte.ts`). Consequences: after an app restart a restored web pane shows "not running"; the log tail is shown on exit only (no live log view). Request: a `tool_status(instance_id) -> {handle, log_tail, exited}` command (or a `tool.updated` UiEvent).
4. **Web pane closed → stop the tool (L2/L3).** Nothing reports a pane removal to the plugin host. Workaround: `WebToolPane` checks on destroy whether its pane is still in the project layout; if not and the tool's lifecycle is `on_close`, it calls `tool_close`. Request: core calls `tool_close` (or publishes `pane.closed`) when a layout change drops a web pane.
5. **`keep_alive` screens (L2).** The shell unmounts inactive tabs, so a plugin iframe can only stay alive while its pane is mounted but hidden (zoom). Request: shell keeps `keep_alive` screen panes mounted (hidden) across tab switches, or the contract drops that case.
6. **Web proxy listener (L7).** `kelta_plugins::proxy::router()` is mountable by kelta-server at `/proxy`, but web tools need a URL before kelta-server's HTTP port is known, so kelta-plugins serves the same router on its own lazy loopback listener (`proxy::ensure_listener`: started by the first proxied instance, then kept; Host header must be loopback:<port>). Decide whether to keep this or pass the server port into the host.
7. **Tool keybindings (L2).** `ToolInfo.keybinding` should dispatch `tools.open` with `{ tool_id }`; the L8 handler opens that tool in the active project (without `tool_id` it opens the tool picker).
8. **Mock IPC (scaffold).** `plugin_inspect`/`plugin_install` always return the `sprint-burndown` fixture. The L8 e2e wraps the transport in `ui/tests/e2e/plugins/harness.ts` to install the real `examples/plugins/hello-screen` (preview generated by `crates/kelta-plugins/tests/install.rs`). Optional request: a `controls.override(cmd, handler)` hook.

## Deviations from the docs

1. **Screen handshake (PLUGINS §7).** The host sends `kelta:init` + `port2` in answer to the SDK's `{type: "kelta:ready"}`, and only when `event.source === iframe.contentWindow`, instead of on the iframe `load` event. This removes the race where a screen's listener is not yet installed at `load`. Doc tweak: "after the screen posts `kelta:ready`".
2. **Screen instances.** Each time the iframe is created the pane opens a fresh instance (`plugin_screen_open`) and closes it when the iframe is destroyed; the instance stored in `PaneContent::PluginScreen` (opened by the backend with the pane) is closed on mount. Theme pushes use a fixed token subset (`--k-bg…`, `--k-fg…`, `--k-accent…`, status colours, fonts, `color-scheme`).
3. **Web pane Relaunch** opens the tool again in a new tab (`tool_open` cannot target an existing pane); the old pane keeps its exit banner until closed.
4. **Web tool iframe sandbox** is `allow-scripts allow-forms allow-same-origin allow-downloads allow-modals`: the tool runs on its own loopback origin (cross-origin to the app), so `allow-same-origin` only gives it its own storage. Only `http(s)` URLs are framed; anything else gets the "Open in browser" card. Plugin screens keep `allow-scripts allow-forms` exactly (ARCH §11.3).
5. **Plugin settings** (`[contributes.settings]`) are provided to kelta-config through `PluginSettingsSource::fragments` + `ConfigService::set_plugin_schemas`; Settings → Plugins does not render its own form, the schema-driven settings form (L4) renders `plugins.<id>`.
6. **Public API additions** on `PluginHost` (signatures of the frozen methods unchanged): `wire`, `is_wired`, `start`, `registry`, `refresh`, `is_enabled`, `granted`, `core`, `dirs`, `grant_store`, and public modules (`manifest`, `perms`, `proxy`, `uri`, `triggers`, …) used by tests.
