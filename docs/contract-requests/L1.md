# L1 contract requests and deviations (kelta-term)

## Requests

1. **`SWALLOWED_QUERIES`: add `XTWINOPS_CHARS`** — `csi("XTWINOPS_CHARS", None, None, "t", &[18])`.
   alacritty_terminal 0.26 answers `CSI 18 t` (text area size in characters, `\e[8;rows;colst`).
   xterm.js does not answer it with its default `windowOptions`, so today it is still answered
   exactly once, but the swallowed list should be the exact answered set
   (`docs/contracts/terminal-queries.md`, checked by `crates/kelta-term/tests/queries.rs`). When
   this is accepted, flip the row's last column to `yes` and drop the `extra` assertion in that test.
2. **Scrollback-cap toast** (ARCH §9.5 "emit toast once"): `TerminalEvent` has no variant for it
   and the host has no `UiBridge`. L1 logs a `tracing::warn!` once per host instead. Proposed:
   `TerminalEvent::MemoryCapReached { cap_mb: u32 }` (emitted once, on the session that triggered
   the shrink) so core can raise the toast.
3. **`terminal.view_scrollback`** is not part of `TerminalLimits`; snapshots use the default
   (`kelta_term::VIEW_SCROLLBACK` = 1000 lines). Proposed: add `view_scrollback: u32` to
   `TerminalLimits` (0 = default) so the setting reaches the encoder through `set_limits`.

## Deviations (local, no contract change needed)

- `PtyTerminalHost::with_backend(env, limits, Arc<dyn PtyBackend>)` and `new_arc` are extra public
  constructors; `new` keeps its signature and picks portable-pty (the rustix openpty/fork backend
  with feature `rustix-pty`). Both backends are always compiled and tested.
- Exited sessions stay in the host (text tail, re-attach gets Snapshot + Exit) until a `spawn`
  reuses the id; `write` to an exited session returns `Conflict`, `kill` is a no-op.
- `stats().sessions[].memory_bytes` is the §9.5 estimate (`history_lines × cols × 24 B` + grid),
  not measured allocation.

## Acceptance notes

- **Parse throughput (≥ 200 MB/s): not confirmed.** `cargo bench -p kelta-term --bench term` on an
  M1 Pro under load average ≈ 21 on 10 cores (nine other lanes compiling) measured ≈ 112 MiB/s on
  the build-log workload (`tests/common/workload.rs`). Raw `alacritty_terminal` `Processor` +
  `Term` on the same input measured 93-121 MiB/s in the same run, and the kelta pre-scan (OSC
  7/9/777 + text tail) runs at ≈ 2 GiB/s, so kelta adds ≤ 7 %; the floor is `Term::input`.
  Re-run the bench on an idle machine; if it still misses, the target needs revisiting against
  alacritty's own throughput (D2), not kelta-term code.
- Snapshot 200×60 + 1000 lines: ≈ 1.2 ms (bench) and ≤ 150 KB (asserted in
  `tests/snapshot_roundtrip.rs`).
- 10 idle sessions × 500 lines: ≈ 14 MB RSS (`tests/resources.rs`). The sessions fill one after
  another: ten readers growing their grids at the same instant measured ≈ 40 MB RSS with the same
  live heap (`malloc_zone_statistics`), i.e. freed-but-retained malloc regions from alacritty's
  1000-row grid growth step, not idle footprint.
